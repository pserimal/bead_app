## 3. 度量定义

全部在 48×48 cell 上、`training/scripts/eval_cell_baseline.py` 复现运行时
契约：BGR→gray letterbox、batch 推理、`constrained_decode`（blank=0，
blank_penalty=2.0）、conf = `exp(score / len(code))`。

- **exact_match（raw）**：不做置信度过滤的 constrained decode top-1 == 标签
  的比例。这是解码质量的真实度量，也是验收规则绑定的数字。
- **UNKNOWN（runtime）**：`code ∉ valid_codes` 或 `conf < min_conf`（0.5）
  被拒绝的比例。当前置信度公式对 T=11 模型严重失准：正确格的
  `exp(score/len)` ≈ 0.002，`min_conf=0.5` 会拒绝**全部** cell → 运行时
  过滤器形同虚设（见 §6 发现 F1）。
- **置信度**：全部 cell 的 mean / p10 / p90。
- **耗时**：CPU 上 batch 推理的 ms/cell（含 decode，不含模型加载）。

## 5. 新 Python image-service 验收规则（不低于基线）

新服务（`ocr_core`，ticket 010）在**同一 checkpoint + 同一 crop/decode 逻辑**
下必须满足：

1. **硬门槛**：zip 集（7630 格）raw constrained decode exact_match **≥ 0.7008**
   （容差 ±0.005，即允许 float/批次顺序噪声，不允许逻辑差异）。由于权重与
   解码均确定，新服务应能逐位复现 5347/7630——容差仅用于防测试环境抖动。
2. **per-code 不低于**：23 个编码各自的 accuracy 不得低于基线（±0.02），
   防止「总体达标但某编码塌方」。
3. **UNKNOWN 语义对齐**：新服务的 `min_conf` 过滤行为必须与基线记录一致
   （当前基线显示旧公式会把全部 cell 判为 UNKNOWN —— 新服务必须修正置信度
   归一化，或显式决策 `min_conf` 语义，并在验收报告中说明）。
4. **耗时上限**：CPU 单 cell ≤ 基线 0.975 ms/cell 的 2 倍（0.975→2.0 ms），
   允许语言/批处理差异，禁止退化到秒级。
5. **后续补充（非本基线门槛）**：当有带网格坐标的 GT（如标注工具补填
   「行/列」列）时，追加图级 exact-match 基线（当前
   `training/scripts/eval_stand.py` 的图级格式），与 cell 级数字一起作为
   完整验收。

**验收执行**：同一脚本 `eval_cell_baseline.py` 指向新服务产出的 checkpoint
路径与实现，对比 JSON 中的 `zip.exact_match_rate` 与 `per_code`。

## 6. 发现（影响 010/014）

- **F1（阻断级）**：运行时置信度公式 `exp(score/len(code))` 对 T=11 CRNN
  失准（正确格 ~0.002），`min_conf=0.5` 会拒绝全部 cell。旧 runtime 在
  CRNN 路径下实际无法产出任何 cell 级结果——这是既有 bug，新服务必须修复
  置信度归一化（或按平均每步 log-prob 归一化）。
- **F2**：`crnn_v2.pt`（config 默认路径）不存在；当前实际基线以
  `crnn_real_m.pt` 为准，新服务的 `MODEL_ARTIFACT_DIR` 契约（010 R3）应直接
  指向 artifact 目录，消除对 config 默认路径的依赖。
- **F3**：constrained decode（运行时路径）显著弱于 greedy（训练评估路径）：
  crnn_real_m 0.7008 vs 0.9308。若 010 的解码器建议改为纯函数时保持
  constrained 语义，验收数字按 constrained（运行时）口径；否则需重跑基线。
- **F4**：dir 集（50 格）含训练词汇表外编码（H15、H21、H33…），模型
  constrained 后几乎全错（0.04）——不应作为新服务验收样本，仅记录。
